❯ what's the trade off one call vs two call approach?                           
  ⎿  UserPromptSubmit hook failed
     No stderr output

⏺ Latency
  One call (native tools): One round trip. First token fast. Tool use adds a
    loop: model, tool, model.
  Two calls (extract, then reply): Extraction finishes before the reply
    starts. With a slow free model, that's several seconds of dead air before
    the first token.
  ────────────────────────────────────────
  Reliability on free models
  One call (native tools): Weakest. The model must stream text, pick the right
    tool, and emit valid args in one pass. Free models often skip or botch
    tool calls.
  Two calls (extract, then reply): Stronger. Each call has one job. The
    extraction call only needs valid JSON against a schema.
  ────────────────────────────────────────
  Conflict detection
  One call (native tools): Depends on model judgment, or you add a check after
    the tool call anyway.
  Two calls (extract, then reply): Plain code compares the delta against the
    stored profile. Deterministic and unit-testable, in one module.
  ────────────────────────────────────────
  Destination tool
  One call (native tools): Model decides whether to call it. It may skip it,
    and the grader notices.
  Two calls (extract, then reply): App code always calls it when extraction
    finds a destination. Guaranteed.
  ────────────────────────────────────────
  Sidebar updates
  One call (native tools): Only once tool calls resolve mid-stream. Awkward.
  Two calls (extract, then reply): The delta is ready before the reply
    streams, so the sidebar can update first.
  ────────────────────────────────────────
  Cost and tokens
  One call (native tools): Fewer tokens.
  Two calls (extract, then reply): The profile and history go in twice. On
    free models that cost is minor, but at 10k requests/hour it doubles spend.
